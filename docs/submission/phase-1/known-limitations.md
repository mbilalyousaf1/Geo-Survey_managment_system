# Phase 1 known limitations

This is the approved **local Docker demonstration and submission** scope. The [acceptance matrix](acceptance-matrix.md) and [validation report](validation-results.md) record the actual final backend, Docker/browser and extracted-source build evidence. Production deployment and separately unperformed live failure drills remain outside those claims.

| Area | Current boundary and practical effect |
| --- | --- |
| Production hosting and residency | Only the server-managed `local-demo` region/profile is selected for this delivery. Production region, Azure hosting topology, data residency, compliance, and operational deployment rules remain unresolved deployment decisions. Local profile selection makes no residency/compliance claim. |
| Administrator delivery | Initial administrator invitations are random, single use, valid for 24 hours, and returned once for manual secure handoff. There is no email provider or automatic delivery/recovery channel. Reissue is allowed only while AwaitingAdministrator and never resets an active account. |
| Ownership repair after a rare interruption | CREATE DATABASE cannot share the global transaction. If a process stops after creating a database but before storing its ownership extended property, subsequent runs preserve the target and fail closed. An authorized operator must verify ownership using the trusted registry and server creation evidence before repairing that property and requesting retry. No public repair endpoint or automatic adoption/deletion exists. Ordinary restarts after a completed tenant commit resume automatically. |
| Cross-database activation | There is no distributed transaction. A tenant grant may remain committed if the later global activation transaction fails. The global account stays passwordless, the invitation remains usable until expiry/reissue, and a retry reuses the grant. Tenant access requires the completed global state and the grant, so the partial result does not authorize sign-in. |
| Authorization scope | Phase 1 stores only initial Organization Administrator grants in each tenant database. Full custom RBAC, multiple roles, permission management, project/geographical assignments, general organization-user administration, and tenant impersonation are not implemented. General RBAC belongs to Phase 2. |
| Account recovery and MFA management | Organization-user MFA rollout remains undecided. The implemented Platform recovery path consumes an already issued single-use recovery code after password verification. Automatic MFA reset, recovery-code regeneration, administrative recovery, and broader account-recovery policy remain separate work. |
| Retention, deletion, and lifecycle management | Failed databases are preserved. No tenant deletion, automatic orphan-database cleanup, finalized retention/erasure policy, billing/subscription workflow, or suspension-management UI/API is included. Existing Suspended registry state is enforced for access. |
| Local operational permissions | The HTTP API has restricted runtime SQL permissions. The separate local worker management credential remains privileged for creation/migration and must be constrained, rotated, and independently operated for production. Hangfire's jobs principal owns only its separate jobs database. The local setup is not a claim of production-grade least-privilege/cloud-identity deployment. |
| Local certificates and secrets | Local generated certificates/secrets are kept outside source and images. They require the runbook's local trust/configuration steps. Production certificate issuance/renewal, managed secrets, backup/restore, disaster recovery, monitoring/alerting, and key lifecycle are not completed by this demo. |
| Browser refresh coordination | The browser uses Web Locks for coordinated cookie-changing operations and BroadcastChannel for account/session changes. A browser without Web Locks requires fresh sign-in at expiry/new tab. Strict refresh reuse detection has no grace period; stale/concurrent clients that bypass coordination can revoke their session family. |
| Temporary setup material | Enrollment state, one-time recovery display, access tokens, and activation fragments are held only in memory. Refreshing a transient enrollment view returns to password entry. The activation page strips its fragment; reopen the private link to resume an unconsumed invitation after refreshing. |
| Frontend dependency audit | The [frontend handover](frontend-flow.md) records remaining transitive development-tool advisories and a separately passing production-dependency audit at that checkpoint. The final validation report must retain actual current audit results. This submission does not claim a clean full dependency audit. |
| Mobile, GIS, and survey features | No mobile acceptance flow, parcel/map/GIS workflow, projects, assignments, GPS capture, photos, survey forms/submission, amendments, reporting, or offline synchronization is delivered in this Phase 1 slice. Existing mobile scaffolding does not establish those capabilities. No sample survey dataset is fabricated. |
| Scale and hardening evidence | The targeted SQL tests establish specified consistency/isolation cases. Production load, penetration testing, high availability, multi-region operations, and long-running failure/recovery exercises remain separate work. Liveness alone is not a readiness or full-stack acceptance claim. |

The global identity/registry model and per-organization operational database architecture are implemented. The tenant baseline intentionally contains only its immutable organization identity and initial administrator grants. Scope boundaries above preserve the master specification's later phases and unresolved business decisions.

The [Postman collection](GeoSurvey.Phase1.postman_collection.json) contains no saved passwords, tokens, recovery material, or response examples. Set its empty placeholders privately in a local environment, use the same HTTPS host/cookie jar for CSRF and refresh, and avoid exporting populated environments or saving sensitive responses as submission evidence.
