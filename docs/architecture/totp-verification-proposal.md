# TOTP primitive proposal

Status: Accepted and implemented, 2026-11-17. The owner approved these parameter and implementation choices. See [ADR 0034](../decisions/0034-totp-primitive.md) and [verification evidence](../development/totp-primitive.md).

## Next bounded task

Add an Identity Infrastructure TOTP generation/verification component with deterministic time and unit tests. This component calculates/verifies codes only; it does not enable MFA, issue authentication tokens, or claim to enforce database replay/attempt limits.

Approved parameters: cryptographically random 20-byte secrets encoded in canonical unpadded Base32; HMAC-SHA1, six ASCII digits with leading zeroes preserved, Unix epoch, and 30-second steps. Accept the current step and one adjacent step in each direction. Return the matched step to the trusted caller so a later transaction can enforce monotonic single-use acceptance.

Use .NET cryptographic primitives and a small RFC 4226/6238 implementation with strict Base32 parsing, explicit bounds, fixed-time code comparison, and an injected TimeProvider. No new dependency or database/API change is included. SHA-1 here is the RFC HMAC-based OTP construction, not a password hash.

## Framework trade-off

The pinned ASP.NET Core Identity AuthenticatorTokenProvider validates five steps (offsets -2 through +2), uses the system clock directly, and returns only a Boolean. The proposed narrower window and matched-step reporting are not configurable through this provider API. Therefore the approved component implements the RFC computation using standard .NET HMAC primitives. This security-sensitive choice received explicit approval and is covered by independent published RFC vectors.

Affected files: new TOTP component under Identity Infrastructure/Mfa, Identity unit tests, accepted ADR after approval, and development notes. Test RFC vectors, matching-step reporting, leading zeroes, invalid inputs, exact window boundaries, random secret encoding/round trips, and dates beyond 2038. Use published vectors; do not validate the implementation only against codes generated by itself.

## Subsequent review boundaries

Before any public confirmation/login flow, separately approve and implement persistent attempt limits across challenge replacement, account/purpose throttling, atomic replay-step enforcement, confirmed-secret storage, recovery codes, and challenge consumption plus MFA enablement. No suggested failure counts/durations are silently accepted by this primitive proposal. A valid calculated code alone must not grant administrator access.

Sources: [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html), [RFC 4226](https://www.rfc-editor.org/rfc/rfc4226.html), and [pinned Identity provider source](https://github.com/dotnet/aspnetcore/blob/v10.0.9/src/Identity/Extensions.Core/src/AuthenticatorTokenProvider.cs).
